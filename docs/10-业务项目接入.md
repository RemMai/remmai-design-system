# 10 — 将 RMDL 接入 A/B/C 业务项目

## 一、三项必要内容

**业务仓库**需要：

1. 项目根的 `AGENTS.md` + `CLAUDE.md` 作为三种 Agent 的规范入口。
2. 明确引用 RMDL 主规范的**固定版本**：推荐 `vendor/rmdl` submodule。
3. 自己的 `rmdl.project.json` 以及真正安装的已发布 RMDL UI/Tokens 包（UI 包尚未发布时不能假称安装成功）。

**不应该**将整个 RMDL 仓库的 UI 源码复制到每一个业务项目；否则又会分叉。业务项目用固定 npm 包依赖，规范用固定 Git 版本/commit。

## 二、结构参考

```text
business-project-A/
├── AGENTS.md                  # 本项目入口，包含读取 vendor/rmdl 的要求
├── CLAUDE.md                  # @AGENTS.md
├── rmdl.project.json          # 本项目技术栈，已得到你的审批
├── .npmrc                     # 只放 registry 地址，不放 token
├── vendor/rmdl/               # submodule，固定 Tag/Commit
├── apps/web/                  # React + TS + Bun + HeroUI + RMDL 组件
├── services/                  # 由你选定语言的后端
└── .github/workflows/         # 业务仓库的 CI（与主规范仓库不同）
```

模板见 `templates/project/`。复制模板前，把 `<OWNER>`、`<APPROVED_TAG>` 等占位符替换，检查导入和实际路径。模板是**起点**，不是已经完整运行的业务工程。

## 三、新建项目与重构

**新建**：让 Agent 首先根据 `docs/01-选型与审批协议.md` 提出问题。前端红线默认锁定，不要求你每次重新回答 React 还是 Vue；需要你做选择的是产品类型、后端、ORM、数据库、部署、认证与其他非红线配置。只有审批后才执行脚手架。

**整体重构**：先读源码→列出现有技术/前端偏差→给出候选方案及影响→等待你确认→分阶段迁移。**严禁直接删库、删页面或大面积替换 UI**。

`rmdl.project.json` 由 v0.3 工具生成：

```bash
node vendor/rmdl/scripts/rmdl.mjs init new --root .
# 核对草稿，由你真实确认后：
node vendor/rmdl/scripts/rmdl.mjs approve --root .
```

`approve` CLI 仅负责登记声明字段，不是可靠的身份校验，必须叠加 PR 审批；更推荐最后由你审阅 `rmdl.project.json` 的 diff。

**注意**：`node vendor/rmdl/scripts/rmdl.mjs ...` 是示例引用路径，接入时检查脚本参数及相对目录。CLI 不是“远端服务”，所有路径都应在本地/CI 上可用。

**版本适配注意**：继承的 v0.3 工具固定校验 `standardVersion: "0.3.0"`、`@remmai/rmdl-ui@0.3.0` 等旧规则；当前 v0.4 文档版本并不代表工具与私有发布包已经升级。务必先保持真实配置与真实依赖一致，待工具升级支持新 scope/版本后再使用正式共享包。不能为了 CI 绿灯虚报依赖。

## 四、运行检查

在 A/B/C 的真实业务项目中：

```bash
node vendor/rmdl/scripts/rmdl.mjs audit --root .
node vendor/rmdl/scripts/rmdl.mjs check --root .
# 补充各项目实际存在的 commands：
bun install --frozen-lockfile
bun run typecheck
bun run lint
bun run test
bun run build
```

`check` 只是基础静态门禁；对于 `DataTable` API、性能、交互、对比截图等，还必须加项目专属 ESLint/Playwright 验证。CI 应作为 Required Status Checks（受 GitHub 套餐权限约束）。

## 五、跨项目升级

A 项目提出公共表格需求→RMDL 主库完成审核发布→A 先试运行→B/C 由依赖升级 PR 引入→每个项目自测、人工验收。不要让 Agent 一次性修改所有项目以“统一风格”，那会扩大风险与工作范围。

## 六、迁移完成的判定

- 业务项目的 `AGENTS.md` 可被 Codex/OpenCode/Claude Code 读取。
- 选型在 `rmdl.project.json` 中锁定且记录审批。
- 正式公共组件通过固定 npm 包导入，不存在私有叉代码。
- 用户页面符合页面契约和视觉基线。
- CI 实际运行、结果 PASS，有可回滚部署。
