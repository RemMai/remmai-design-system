# 10 — 将 RMDL 接入 A/B/C 业务项目

## 一、必要内容

**业务仓库**需要：

1. 使用 OpenCode 时，项目根 `AGENTS.md` + `opencode.json` 是规则入口。自动接入目前只提供 OpenCode/跳过；其他 Agent 后续添加，既有 CLAUDE.md 模板不由脚本自动安装。
2. 明确引用 RMDL 主规范的**固定版本**：推荐 `vendor/rmdl` submodule。
3. 自己的 `rmdl.project.json` 以及真正安装的已发布 RMDL UI/Tokens 包（UI 包尚未发布时不能假称安装成功）。
4. 根 `opencode.json` 显式加载短基线，根 `VERSION` / `CHANGELOG.md` 绑定产品版本；按 [16](16-产品版本与构建标识.md) 接入构建元数据。已有 OpenCode 配置只合并 instructions。

**不应该**将整个 RMDL 仓库的 UI 源码复制到每一个业务项目；否则又会分叉。业务项目用固定 npm 包依赖，规范用固定 Git 版本/commit。

## 二、结构参考

```text
business-project-A/
├── AGENTS.md                  # 本项目入口，包含读取 vendor/rmdl 的要求
├── CLAUDE.md                  # @AGENTS.md
├── rmdl.project.json          # 本项目技术栈，已得到你的审批
├── .npmrc                     # 只放 registry 地址，不放 token
├── vendor/rmdl/               # submodule，固定 Tag/Commit
├── apps/web/                  # 工程化 React 前端，或锁定 static-html 的原生静态页
├── services/                  # 由你选定语言的后端
└── .github/workflows/         # 业务仓库的 CI（与主规范仓库不同）
```

模板见 `templates/project/`。复制模板前，把 `<OWNER>`、`<APPROVED_TAG>` 等占位符替换，检查导入和实际路径。模板是**起点**，不是已经完整运行的业务工程。

## 三、新建项目与重构

**新建**：让 Agent 首先根据 `docs/01-选型与审批协议.md` 提出问题。需要选择产品类型、前端实现模式（工程化 / 原生静态页 / 无 Web）、工程化框架、后端、ORM、数据库、部署和认证。两种 Web 模式都遵守 RMDL 视觉契约；只有审批后才执行脚手架。

**整体重构**：先读源码→列出现有技术/前端偏差→给出候选方案及影响→等待你确认→分阶段迁移。**严禁直接删库、删页面或大面积替换 UI**。

`rmdl.project.json` 由 v0.3 工具生成：

```bash
node vendor/rmdl/scripts/rmdl.mjs init new --root .
# 核对草稿，由你真实确认后：
node vendor/rmdl/scripts/rmdl.mjs approve --root .
```

`approve` CLI 仅负责登记声明字段，不是可靠的身份校验，必须叠加 PR 审批；更推荐最后由你审阅 `rmdl.project.json` 的 diff。

**注意**：`node vendor/rmdl/scripts/rmdl.mjs ...` 是示例引用路径，接入时检查脚本参数及相对目录。CLI 不是“远端服务”，所有路径都应在本地/CI 上可用。

**版本适配注意**：继承的 v0.3 工具固定校验 `standardVersion: "0.3.0"`、`@remmai/rmdl-ui@0.3.0` 等旧规则；当前 v0.4 文档版本并不代表工具与私有发布包已经升级。务必先保持真实配置与真实依赖一致，待工具升级支持新 scope/版本后再使用正式共享包。不能为了 CI 绿灯虚报依赖。

## 四、运行检查

在 A/B/C 的真实业务项目中：

```bash
node vendor/rmdl/scripts/rmdl.mjs audit --root .
node vendor/rmdl/scripts/rmdl.mjs check --root .
# 补充各项目实际存在的 commands：
npm ci
npm run typecheck
npm run lint
npm run test
npm run build
```

上述 npm 命令在 `package-lock.json` 所属工作区执行；独立前端先进入 `apps/web`，npm workspaces 则在根目录按真实 scripts 或 `--workspace` 参数运行。Node.js LTS 与 npm 版本按主规范 5.2 固定。`check` 只是基础静态门禁；对于 `DataTable` API、性能、交互、对比截图等，还必须加项目专属 ESLint/Playwright 验证。CI 应作为 Required Status Checks（受 GitHub 套餐权限约束）。

从旧工具链升级时须同步迁移 `rmdl.project.json`：增加 `fixed.runtime: "node"` 并将 `fixed.packageManager` 改为 `"npm"`，按 [ADR-0001](decisions/ADR-0001-nodejs-npm.md) 更新依赖、脚本与锁文件。升级 submodule 本身不会自动修改业务配置；新检查器会拒绝旧选型和旧锁文件。

本次 .NET 11/版本治理修订另需 `fixed.dotnetTarget: "net11.0"`、`versioning`，以及真实产品 VERSION/CHANGELOG；.NET 应用补全 SDK 锁与 TFM。按 [ADR-0002](decisions/ADR-0002-dotnet11-product-version.md) 审查迁移，不伪造原来的审批。运行 `node vendor/rmdl/scripts/rmdl.mjs version --release --root .` 生成发布元数据，并实际接入前后端构建。

## 五、跨项目升级

A 项目提出公共表格需求→RMDL 主库完成审核发布→A 先试运行→B/C 由依赖升级 PR 引入→每个项目自测、人工验收。不要让 Agent 一次性修改所有项目以“统一风格”，那会扩大风险与工作范围。

## 六、迁移完成的判定

- 业务项目的 `AGENTS.md` 可被 Codex/OpenCode/Claude Code 读取。
- 选型在 `rmdl.project.json` 中锁定且记录审批。
- 正式公共组件通过固定 npm 包导入，不存在私有叉代码。
- 用户页面符合页面契约和视觉基线。
- CI 实际运行、结果 PASS，有可回滚部署。

## 七、标准管理脚本

Windows 双击标准仓库根 `rmdl.cmd`，或运行 `node <标准仓库>/scripts/bootstrap.mjs`。不带 `--action` 时启动菜单：

```text
RMDL 标准管理
  1. 初始化标准
  2. 更新标准
  3. 检查项目
  4. 更新并检查
  0. 退出
```

操作中选择目标目录、Agent 规则（OpenCode 默认 / 跳过）、标准引用、可选 HTTP 代理。`rmdl.cmd` 支持单文件复制到目标目录后双击，默认选择启动器所在目录。已有标准子模块包含此脚本时，也可在业务根运行 `node vendor/rmdl/scripts/bootstrap.mjs`。

### 检查项目

菜单 **3. 检查项目** 或 **4. 更新并检查** 会先运行标准门禁，再按需运行工程检查；初始化/更新成功后也会询问是否立即检查。检查范围：

- **仅标准门禁**：`vendor/rmdl/scripts/rmdl.mjs check`。
- **标准 + 工程检查**：在标准门禁后，对根目录和 `apps/web` 中实际存在的 `package.json` 脚本依次执行 `typecheck`、`lint`、`test`、`build`；找到 `.sln`/`.slnx` 且本机有 dotnet 时执行 `dotnet build -c Release`。

输出逐项 PASS / FAIL / NOT RUN 与汇总。未定义脚本、缺少 dotnet、未配置视觉回归记为 NOT RUN，不视为通过；任一 FAIL 使检查命令返回非零。检查不修改项目文件，也不代替 Playwright 视觉对比与人工审查。非交互用法：`--action check --checks standard|project`。

启动器依次使用旁边的 `scripts/bootstrap.mjs`、已安装的 `vendor/rmdl/scripts/bootstrap.mjs`、全局 `rmdl/scripts/bootstrap.mjs`；都没有时，通过 Git 克隆工具到独立临时目录，启动菜单并在退出后清理。使用已存在的脚本不会自动切换业务标准版本。私有仓库通过现有 Git 凭据访问；Windows 优先使用显式/环境/Git 代理，其次读取已启用的系统 HTTP 代理。可传入 `--proxy` 或设置 `RMDL_PROXY`，不会改写机器配置。

独立下载工具的仓库和分支可分别用 `RMDL_BOOTSTRAP_REPOSITORY`、`RMDL_BOOTSTRAP_REF` 指定；默认分支当前为 `chore/dotnet11-product-version-standards`，因为安装工具尚未合并 main。工具引用仅决定启动哪份脚本，业务标准版本仍在菜单中选择。若出现 `Cannot find module ...scripts/bootstrap.mjs`，说明仍在使用需要完整目录的旧启动器，替换为最新 `rmdl.cmd` 即可。

### 初始化行为

- 需要 Node.js 和 Git，使用现有 Git 凭据，不存储 token。私有库访问失败应先恢复 Git 认证。
- 只接受空目录或父目录已存在的新目录。唯一例外为正在运行的单文件 `rmdl.cmd`，会保留原文件并纳入暂存；其余文件（含隐藏文件和 `.git`）都会阻止初始化。
- 先在目标旁临时目录完成 clone、版本解析、模板验证，再放入目标目录；失败清理本次创建的内容，不留下半套工程。
- 默认仓库为 `https://github.com/RemMai/remmai-design-system.git`。从标准仓库启动时默认选择其当前分支（detached 时为当前 commit），独立脚本默认远端 HEAD。指定引用必须已经推送到远端。
- 固定标准到 `vendor/rmdl` submodule 的精确 commit；`rmdl.bootstrap.json` 记录仓库、选择引用、实际 commit、Agent 模式和等待选型状态。这是接入记录，不是所有者审批记录。
- OpenCode 模式只生成根 AGENTS.md 和 opencode.json；跳过模式不生成 Agent 入口。不自动生成 VERSION 或审批草稿，产品版本随实际选型/发布计划确定。
- 初始化将新文件暂存，但不创建业务提交、不绑定业务远端、不推送、不执行产品构建。

### 更新行为

- 只在业务 Git 根目录更新已登记的 `vendor/rmdl` 子模块；已克隆但未初始化的子模块先运行 `git submodule update --init --recursive`。
- 检查子模块无本地修改，获取远端引用后解析所选 commit。分支名优先使用新抓取的远端分支，避免误用过期本地分支。
- 校验目标标准与规则模板，再切换版本。业务选型和版本文件不改写，更新失败尝试恢复旧 checkout 和被管理文件的原始内容。获取远端对象本身不回退。
- OpenCode 模式自动更新未被自定义修改的 AGENTS.md；opencode.json 合并 instructions、保留模型等其他配置。发现自定义 AGENTS.md 或额外 `.jsonc` / `.opencode` 配置入口时停止该自动更新，提示人工合并或选择跳过。
- 跳过只代表本次不安装/同步 Agent 规则，已有 Agent 文件保留。需要禁用既有规则时由项目所有者另行处理。
- 标准更新可能新增门禁要求，脚本成功不代表业务合规。输出旧/新 commit，保留可审查的未暂存 diff；开发者完成迁移、测试和审查后提交。

### 非交互参数

```bash
node /path/to/rmdl/scripts/bootstrap.mjs --action init --root /path/to/new-product --agent opencode --ref main
node /path/to/rmdl/scripts/bootstrap.mjs --action init --root /path/to/new-product --agent skip --ref main
node /path/to/rmdl/scripts/bootstrap.mjs --action update --root /path/to/product --agent opencode --ref main
node /path/to/rmdl/scripts/bootstrap.mjs --help
```

`--repository` 可指定标准镜像仓库；更新始终使用已安装子模块的 origin，不悄悄更换来源。需要代理时加 `--proxy http://127.0.0.1:7890`（端口以本机实际配置为准）；仅对此次 Git 网络操作生效，不更改全局代理。环境已有 Git 代理时直接留空即可。

未合并的标准改动只存在于功能分支时，选择该已推送分支或精确 commit，不能从 main 假称已取得最新功能。正式采用哪个标准版本由项目所有者决定。

### 验证和回滚

安装后运行 `git submodule status`，核对结果与 `rmdl.bootstrap.json.commit`；OpenCode 模式检查根 instructions 指向的基线文件存在。主库测试 `node --test tests/rmdl-bootstrap.test.mjs` 使用本地临时 Git 仓库，覆盖菜单、OpenCode/跳过、初始化、版本选择、更新、定制配置保护和失败清理。

业务更新的回滚以审查过的升级提交为单位，恢复旧标准 gitlink、入口文件和接入记录，并运行 `git submodule update --init --recursive`。更新尚未提交时，应按自己的 diff 恢复本次修改，不能整仓 `reset --hard` 丢弃其他工作。初始化没有外部发布副作用；确认没有新增业务工作后，可移除本次新项目目录重新接入。
