# 07 — 公共组件 Registry 与 A → B 组件晋升机制

## 一、唯一标准的判定

**只有以下条件同时满足**，B 项目才可以把某组件视为正式 RMDL 标准：

1. `registry/components.json` 条目状态为 `approved`。
2. 具有可安装包、已发布版本和清晰导出 API。
3. 有你审定的视觉与行为规范、测试及兼容范围。
4. B 项目明确固定依赖版本，并通过 CI 与页面验收。

没有这四条，即使 A 项目里表格“看起来不错”，也不能假装是正式标准。

## 二、组件生命周期（必须遵守）

`proposed` → `candidate` → `approved` → `deprecated` → `retired`

- `proposed`：A 项目提出，可能还包含业务耦合；只能讨论，不允许作为正式包消费。
- `candidate`：移入主库进行抽象，设计 API、状态样例、无障碍、键盘交互、性能与测试。
- `approved`：**所有者批准 + 版本已经发布**，才能在业务中强制复用。
- `deprecated`：兼容保留，必须公布替代组件与迁移周期。
- `retired`：不再提供新版本；迁移完成后才能物理删除。

不得由 Agent 自行将 `candidate` 改为 `approved`。状态变更必须配合 GitHub PR 审批记录与 release 证据。

## 三、A 项目中的表格如何晋升

**A 项目**：你认可用户表格的交互和视觉，创建 PR/Issue，记录截图、需求、代码位置和定制点。

**RMDL 主库**：UI Maintainer 抽离业务字段与 API 访问；将列定义、排序、分页、加载、筛选、选择、操作槽位抽象为稳定接口。复用现有 HeroUI v3，不复制第二套组件系统。完善 Storybook/文档站演示或等效预览。

**评审**：运行 Light/Dark、1440px/390px、长字符串、多语言、空/异常/大数据、键盘操作等用例。你在 PR 中确认“这是标准表格”。

**发布**：为 `DataTable` 指定公开导出、稳定版本、变更日志、可安装产物，更新 Registry 为 approved。

**B 项目**：固定版本安装并使用 `DataTable`，业务只传 columns/data/可选行为，不复制表格 DOM/CSS。

## 四、表格 API（仅提案，不代表已实现）

```tsx
import { DataTable } from '@YOUR_GITHUB_OWNER/rmdl-ui';

<DataTable
  columns={[
    { key: 'name', header: '商品名称' },
    { key: 'stock', header: '库存' },
  ]}
  data={products}
  rowKey={(row) => row.id}
  pagination={{ page, pageSize, total, onChange: setPage }}
  emptyText="暂无商品"
/>
```

这只是目标接口草案。项目中的真实实现和类型声明完成之前**不要复制粘贴当作可运行代码**。

## 五、组件的“不可变”和“可配置”边界

**不能由业务项目改变**：布局标尺、颜色语义、基础行高、边框/阴影、字体体系、操作按钮层级、空/加载/错误状态模式、响应式阈值的视觉实现。

**业务可以配置**：字段、列标签、API 数据、权限、排序选项、分页总量、业务操作回调、少量经批准的变体。

组件无法满足业务时：先提出扩展公共 API 的提案；不要在 B 项目另写“同名组件”或注入深层 CSS。

## 六、Registry 记录规范

见 `registry/components.json`。每条记录至少包含 `id/name/status/package/export/version`，需要加上 `source`、`ownerApproval`、`visualReference`、`reviewNotes`。未发布的组件 `version` 使用 `null`。

- Registry 不是包管理器，也不自动生成组件源码。
- `version` 必须是实际已发布可安装版本，不能让 Agent 凭空填写。
- `ownerApproval` 是 GitHub 审批/Issue/PR 链接，不得通过字符串“approved”冒充批准。
- 主库与业务库的 CI 应核对版本及禁止重复 UI 组件，但机器无法完全判定视觉美感。

## 七、维护既有项目

业务项目不得直接修改标准包。若 A 需要修复 DataTable，先在主库 patch 版本验证修复，再向 A/B 分别提出依赖升级 PR；任何升级都应该可回滚。
