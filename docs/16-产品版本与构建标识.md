# 16 — 产品 Version、Git 构建标识与前后端绑定

## 1. 三种版本分别管理

| 名称 | 来源 | 示例与用途 |
|---|---|---|
| 产品版本 `version` | 产品根 `VERSION` | `1.1.3`，自行定义的发布版本，前后端共同绑定 |
| 内部标号 `gitCommit` | 构建时实际 `git rev-parse HEAD` | 完整 40/64 位 Git hash，定位构建源码 |
| 规范/依赖版本 | submodule、选型锁、依赖锁 | RMDL、.NET 11、UI 包版本，不替代产品版本 |

`MAJOR.MINOR.PATCH`：不兼容变更 / 兼容的新功能或小更新 / 兼容的 bug 修复。升主版本时后两段归零，升次版本时修订段归零。初始产品版本由产品发布计划确定，`1.1.3` 仅为示例。只有实际准备发布的变更才更新发布版本；不能每个 session 自动加版本。

根 `VERSION` 仅包含三段数字，无 `v` 前缀、前导零或 hash。根 `CHANGELOG.md` 必须有当前版本的 `## 1.1.3` 或 `## [1.1.3] - YYYY-MM-DD` 标题，并记录该版本实际变更。`Unreleased` 可另设，但不能替代当前版本记录。

## 2. 构建一次，前后端消费同一份元数据

```bash
# 开发构建：stdout 输出真实元数据，dirty 表明未提交的修改
node vendor/rmdl/scripts/rmdl.mjs version --root .

# 正式构建：必须有真实 HEAD，且源码工作区干净
node vendor/rmdl/scripts/rmdl.mjs version --release --root .
```

命令输出 JSON，字段为 `version`、`gitCommit`、`informationalVersion`、`dirty`。正式 `informationalVersion` 为 `<version>+<完整hash>`，开发脏工作区追加 `.dirty`。缺失 VERSION、错误格式、无 Git HEAD 时失败；正式构建发现已跟踪或未忽略的新文件时失败。不要手填一个“看起来像 hash”的值。

在安装/生成产物之前生成元数据，并在同一流水线中提供给前后端构建。文件写入已由项目明确忽略的制品目录，或 CI 制品暂存区，避免生成物让下一次 release 检查变脏。若用 shell 重定向，先检查退出码；失败输出不能进入构建。发布不得用 `|| true`。

- React/Vite/Next：构建适配器读该 JSON，注入前端版本常量或随制品部署的元数据文件。前端显示其自身构建版本；不向后端查询后直接冒充前端版本。若另外展示后端版本，要明确标注。
- static-html：打包时将相同 JSON 复制为静态版本资源并绑定标签，或发布前渲染到 HTML。工具仅用于发布准备，不要求网站运行 Node.js；元数据和页面必须一起上传并验证缓存更新。
- 后端：把 JSON 或等价的生成常量嵌入制品。HTTP Host 提供 `/api/version`（按项目既有认证策略），CLI 提供 `--version`，Worker 在启动日志或运维接口中提供以上四个字段。运行环境没有 `.git` 时也必须正常返回。
- Docker/其他发布包：OCI 标签 `org.opencontainers.image.version` 和 `org.opencontainers.image.revision` 绑定相同值。流水线号、时间可额外携带，但不替代 Git hash。
- 分仓前后端在发布编排中校验产品 `version` 相同，各自 hash 来自各自源码仓库。滚动发布可暂存多版本，但每个实例必须报告自己的真实版本。

## 3. .NET 11 标准

应用 `TargetFramework` 使用 `net11.0`（平台专属 TFM 可带对应后缀）；根 `global.json.sdk` 必须包含经过验证的精确正式 `11.x` SDK、`allowPrerelease: false`、`rollForward: "disable"`。不要猜测补丁版本；从实际安装/官方可用 SDK 中选择并验证 FreeSql、Provider、认证依赖、CI 与容器镜像。缺 SDK 报告失败原因，不自动降级到 10。

MSBuild 属性从构建 JSON 注入：

| 属性 | 值 |
|---|---|
| `Version` | `version` |
| `SourceRevisionId` | `gitCommit` |
| `InformationalVersion` | `informationalVersion` |
| `IncludeSourceRevisionInInformationalVersion` | `false`，因为已明确提供含 hash 的完整值 |

不要将 `+hash` 放进只接受数字的 `AssemblyVersion`/`FileVersion`。SDK 版本和产品版本分别锁定；`dotnet --version` 验证工具链，API/程序集元数据验证产品。

本次更新的是应用标准及校验器。仓库现有 `RemMai.Rmdl.Auth` 包仍声明 net10.0/net8.0；这是既有共享库目标框架，不能据此声称已经完成 .NET 11 包构建/兼容验证。业务迁移必须在 net11.0 Host 上执行集成测试；共享包扩展目标框架另按组件变更验收。

## 4. 前端位置与验收

严格遵守 **Footer > Menu 底部 > Header 右侧 > 独立更新日志菜单页**，参见 [02 第 11 节](02-前端视觉与页面契约.md#11-产品-version-展示所有-web-形态)。菜单页兜底必须可进入，并展示当前版本与更新记录。更高优先位置不可用的原因记录在 `docs/ui-design.md`。

`rmdl.project.json` 声明：

```json
{
  "versioning": {
    "source": "VERSION",
    "buildId": "git-commit",
    "frontendPlacement": "menu"
  }
}
```

无前端服务使用 `frontendPlacement: "none"`。`fixed.dotnetTarget` 固定 `net11.0`，只在选用 .NET 时要求对应 SDK/工程文件。

验收必须覆盖：

1. 静态门禁：版本三段格式、当前 changelog 标题、配置字段；.NET 选型检查 global.json 和 .csproj/最近的 Directory.Build.props 中的 TFM。此检查只解析字面声明；复杂 MSBuild 求值必须由真实构建补充。
2. 构建绑定：同一 CI 检查前端版本资源、后端版本入口、程序集/镜像标识与 VERSION、真实 HEAD 一致；测试失败阻断发布。仅生成 JSON 不等于前后端已接入。
3. UI：浏览器断言可见 `Version <实际产品版本>`，验证位置优先级、窄屏、折叠菜单、长菜单、账号操作与独立滚动。兜底页需验证导航和更新记录。
4. 回滚：恢复已保存的完整前后端制品及其元数据，确认页面/API 返回旧制品的真实版本；不能只改显示字符串假装回滚。

## 5. 已有项目升级

先记录旧标准 commit、选型和验证基线，再审查升级本次标准 commit；补 `fixed.dotnetTarget`、`versioning`、VERSION、CHANGELOG.md、构建绑定和 .NET 11 SDK/TFM。保留历史审批，新增迁移决定记录；不要冒充过去已经批准这些新增字段。新版静态门禁会拒绝缺少新增字段的旧配置。

同步根 AGENTS.md 与 OpenCode 配置，运行静态门禁、真实 build/test、API 元数据测试和 UI 视觉验证。通过后按发布流程交付；本次标准修订没有自动迁移任何外部业务项目。
