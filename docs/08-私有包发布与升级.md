# 08 — GitHub Packages 私有 UI 包发布与跨项目更新

## 一、推荐结构

- 私有 GitHub 仓库：`<OWNER>/remmai-design-system`
- UI 包：`@<OWNER>/rmdl-ui`
- Tokens 包：`@<OWNER>/rmdl-tokens`
- 版本：语义版本（例 `1.2.3`）和不可变 Git tag
- 消费者：A/B/C 业务项目各自固定安装精确版本 + 锁文件

**注意**：GitHub Packages 的 npm 包 scope 通常应与你的 GitHub 用户名或组织名一致。`@remmai/rmdl-ui` **只有在 GitHub 用户/组织为 `remmai` 时才可直接沿用**。若你的 GitHub Owner 不是 `remmai`，发布前要同步修改包名、导入路径、组件 Registry、工作区和文档。此处 `<OWNER>` 是占位符，不是已知身份。

## 二、v0.3 源码距离真正发布还差什么

当前 `packages/ui/package.json` 含 `"private": true`，导出指向 `src/*.ts(x)`，仅适合开发时直接源码引用；**尚不能按文档中的命令直接发布给跨仓库项目**。

正式发布之前完成：

1. 选择工具将 TS/TSX 编译为 `dist` JS，生成 `d.ts` 类型和 CSS 产物；构建、测试与产物核对。
2. 更新 `exports` 指向 `dist`，设置 `files: ["dist"]`；将 `private` 改为 `false`（表示 npm 可发布，**不表示 GitHub 仓库公开**）。
3. 设置 `publishConfig.registry = "https://npm.pkg.github.com"`，作用域与 GitHub Owner 匹配。
4. Peer dependencies 明确 React 19、HeroUI v3、样式环境；确保包能在独立 consumer 真实安装、编译与渲染。
5. 补 DataTable 等正式组件、演示文档、视觉/无障碍/行为测试、release notes。
6. 只在通过所有者 PR 审批后从受信任的 GitHub Actions 发布，产物和 Tag 可追踪。

**现有 v0.3 业务检查器的兼容性限制**：`scripts/rmdl.mjs` 还把共享包名 `@remmai/...` 和版本 `0.3.0` 写死。将包发布到新的 GitHub Owner 后，必须先为检查器加入“从已审批配置读取包名与准确版本”的实现、对应测试和迁移说明，才可以要求业务仓库通过新版私有 npm 包检查。不能只改 `.npmrc`，也不能为让检查通过继续伪装旧版本。

## 三、凭据与访问

在项目级 `.npmrc` **只写无密钥的 registry 声明**：

```ini
@YOUR_GITHUB_OWNER:registry=https://npm.pkg.github.com
```

认证通过本机 `~/.npmrc` 或环境变量注入，**绝对不要提交真实 token**。GitHub Packages 的 npm registry 常见用法是 PAT (classic)；发布流程可以使用当前仓库的 `GITHUB_TOKEN`，跨私有仓库安装时，先给消费仓库 GitHub Actions 授予包的读取权限，不能访问才评估最小权限的 PAT。对于本机使用，token 需要适合的 `read:packages` 及仓库访问授权。

```ini
# 仅作为用户主目录 ~/.npmrc 的配置示意；不要提交
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

`NODE_AUTH_TOKEN` 从环境安全传入；不要直接写在命令行历史、日志、Issue 或聊天中。

## 四、消费业务项目

在 A/B 业务项目中使用**真实 Owner**安装准确版本，例如：

```bash
bun add @YOUR_GITHUB_OWNER/rmdl-ui@1.0.0 --exact
```

命令只在 `1.0.0` 已发布、认证有权限、包名与 Owner 匹配后才会成功。保留并提交 Bun 锁文件（版本依项目实际 Bun 版本），CI 使用 frozen lockfile。依赖声明及实际解析版本都应被验证，不允许 `latest`、`*` 或随意更新范围。

## 五、版本策略

- `patch`：兼容修复、无意图上的视觉重大变化；仍跑回归。
- `minor`：向后兼容增加可选能力/变体；需要 Demo 与截图证明旧状态不变。
- `major`：Breaking API、DOM 语义、重大视觉基线或交互改变；需要迁移指南、owner 特别批准。
- `0.x`：可作为预发布实验阶段，业务大范围接入前仍需显式约束。

A 升级到 `1.1.0` 不强迫 B 自动更新。Renovate/Dependabot 可为 B 发 PR，但由人审查、CI 验收后才合并；不让 Agent 越权更新所有系统。

## 六、回滚

如果 `1.1.0` 引入问题，B 项目把依赖和锁文件回退到先前版本、重新执行 CI、部署回滚。严禁覆盖同一个已发布版本号的内容（不可变发布）。
