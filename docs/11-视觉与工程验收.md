# 11 — 设计一致性、文案密度和视觉验收

## 一、为什么光靠 Tokens 不够

“颜色一致”≠“页面一致”。统一前端还需要统一 Shell、导航、表格、表单、操作按钮、空状态、间距、语义和响应式行为。以公共组件源码为准，业务只能配置数据与业务行为。

## 二、页面必须通过的检查表

### 信息架构与文案

- 每个页面只有一个清晰的标题和一段必要时才出现的说明。
- 不为了填空白添加无意义欢迎语、KPI 卡片、过长前言、重复提示和密集按钮。
- 主要操作优先级明确；破坏性操作需要确认；筛选栏以查询效率为第一目标。
- 所有字段标签、错误提示、状态和操作命名与同类页面一致。

### 布局与组件

- 使用 `AppShell / AppPage / AppPageHeader / AppToolbar / AppSection` 等公共容器（或正式发布版中对应的导出）。
- 表格、弹窗、筛选栏、空状态等优先使用 Registry 中已批准且可安装的组件。
- 不直接复制基础 UI DOM、禁止第二套组件库、禁止随意覆盖全局 CSS 和 Token。
- 深浅色、键盘导航、焦点可见性、错误反馈等基础行为一致。

### 截图基线

至少覆盖：1440px 桌面 + 390px 移动端；Light + Dark；正常/空/加载/错误状态。交互密集的组件还要有 Hover/Focus/Disabled/Selected 状态。截图基线由你确认；任何 Agent 不得为让测试变绿而单独更新 golden snapshots。

## 三、可执行检查层次

| 门禁 | 验证内容 | 当前状态 |
|---|---|---|
| v0.3 `rmdl.mjs check` | 选型、部分依赖、部分源码违规模式 | 已有最小实现 |
| TypeScript strict / ESLint / Stylelint | 类型、导入边界、硬编码样式、违禁导入 | 需结合实际应用实现 |
| Unit / Component Tests | API、排序分页、空状态、键盘行为 | 完整组件上线前需实现 |
| Playwright Visual | 截图和人类已审定基线对比 | 需配置及生成真实基线 |
| PR Review | 视觉和交互主观判断、业务适配 | 必须由所有者/受托 Reviewer 执行 |

**重要**：若某项尚未配置或未实际执行，报告 `NOT RUN`；不能自称所有门禁通过。GitHub Actions 中的空壳命令也不等于真正测试。

## 四、表格必须审查的状态

- 分页：第一页/末页、总条数为 0、数据刷新时页码合法性。
- 排序：单/多字段策略；后端排序是否与 UI 一致。
- 操作：权限、危险操作提示、多选、批量操作是否导致误触。
- 数据：长文本、空值、金额/时间格式、国际化、大量列横向溢出。
- 无障碍：`table` 语义、列头、焦点、键盘、读屏标题。
- 性能：大数据时是否采用服务端分页/虚拟列表（由实际性能测量决定）。

## 五、失败处理

对比差异必须区分“有意变更”与“回归”。有意变更需要：提案→你确认→更改公共组件→更新截图→发布新版本→业务升级；回归必须先修复，不允许 Agent 直接更新 snapshots。
