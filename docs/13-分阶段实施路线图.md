# 13 — RMDL v0.4 实施路线图

这里按依赖顺序实施，**先能跨 Agent 持续复用，再追求复杂的组件治理平台**。

## 阶段 0 — 创建私有主仓库

交付：GitHub Private 仓库、README/AGENTS/CLAUDE、规范文档、Registry、基本 CI 通过。
验收：三个 Agent 在主仓库能说明 RMDL 的强制原则，且不会直接把业务代码写入规范库。

## 阶段 1 — 统一接入两个真实项目

交付：A/B 各自的根 Agent 规则、固定 RMDL commit、`rmdl.project.json`、业务仓库 CI。
验收：三个 Agent 随机分配同一任务时，都先检查锁定选型和组件 Registry，不自行替换前端技术栈。

## 阶段 2 — 将 RMDL UI 包真正发布

交付：可构建/有类型声明/可安装的 RMDL UI 与 Token 包；真实 Consumer 集成测试；固定版本发布与认证。
验收：A/B 都能通过 GitHub Packages 安装同一个版本并显示同一个 AppShell；没有直接复制包源码。

## 阶段 3 — 第一个正式 DataTable

交付：从 A 认可表格提案出发，抽象为通用组件，完成示例、交互、Visual/Light/Dark、无障碍测试与 owner 批准。
验收：Registry 为 approved，已有 GitHub release；B 只通过 props 展示不同业务数据，页面视觉契约一致。

## 阶段 4 — UI 模板体系

交付：列表页、详情页、编辑页、弹窗、筛选条、空状态的固定模板；文案密度 lint / 评审清单。
验收：两个后台的导航、页面结构和核心操作位置整体一致；既有业务能力不退化。

## 阶段 5 — 持续更新与版本自动化

交付：Renovate/Dependabot 升级 PR、Release Notes、弃用周期、组件预览、可回滚的跨项目升级节奏。
验收：A 升级一个可选表格能力，B 原版本不变化；B 的升级 PR 经独立验收后才合并。

## 明确暂不追求

- 不需要一开始建大型文档网站、复杂的发布门户或者自己开发 npm registry。
- 不需要让 Agent 为追求统一先整体重写所有老系统。
- 不需要把每个业务按钮和表单都抽成通用组件；公共组件必须具备跨场景可复用性。
