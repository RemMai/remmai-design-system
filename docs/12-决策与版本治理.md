# 12 — 选型锁、ADR、审批和版本治理

## 一、谁能做决定

| 决策 | 提案者 | 最终批准 |
|---|---|---|
| 新业务项目后端语言/ORM/数据库 | 根 Agent | 项目所有者（你） |
| 整体重构和破坏性迁移 | 根 Agent | 项目所有者（你） |
| 改变 RMDL 强制前端技术栈 | 需有详细 ADR | RMDL 所有者（你） |
| 设计 Token / 公共组件正式外观 | UI Maintainer | RMDL 所有者（你） |
| 把候选组件变为 approved | UI Maintainer | RMDL 所有者（你） |
| 公共包发布 major / 黄金截图更新 | 维护者提案 | RMDL 所有者（你） |
| 业务页面非破坏性实现细节 | 业务 Worker | 根 Agent 验收，必要时 owner 抽查 |

“Agent 自行填写审批字段”不构成批准。“用户没有否决”也不等于批准。审批必须可追溯到实际由你操作的 GitHub PR / Issue / 明确聊天答复，再落实到仓库记录。

## 二、固定版本策略

- 规范版本：RMDL `v0.4`；Git Tag（如 `rmdl-v0.4.0`）对应不可变规范快照。
- 组件包：独立语义化版本（如 `@OWNER/rmdl-ui@1.0.0`），发布后不能同号覆盖。
- 业务项目：`rmdl.project.json` 锁技术；`bun.lock` 锁依赖；submodule commit 锁规范。
- 业务项目可在不同时间升级，不要求所有应用同时追最新版。

## 三、ADR 提交条件

以下情况必须写 ADR：技术栈例外、核心页面模式变更、跨项目公共组件 API Breaking Change、改变可访问性或交互原则、要替换既有核心依赖。使用 `docs/ADR-template.md`，记录现状、备选、理由、风险、回滚和**真实审批证据**。

## 四、PR 和 Owner 审批

- 主分支禁止直接作为 Agent 写入目标，优先 feature branch / PR。
- 尽量启用 Required Status Checks 和 Code Owners Review；需注意 GitHub 私有库套餐限制。
- CODEOWNERS 中包含 `.github/` 与规则文件本身；避免 Agent 通过改规则绕过检查。
- 用户亲自审查组件截图与 Golden Changes；不接受“截图相似度很高”代替审查。

## 五、质量门禁不得成为形式主义

不得在原有测试失败时加 `|| true`，不得删除检查规则降低门槛，不得无审批把某项测试挪为非阻断。不可以用提升 `major` 版本的方式自动绕过要求；版本号只是变更沟通契约。

## 六、低预算实施建议

如果当前 GitHub 账户方案无法对私有库启用分支保护，可以先做到：

- Agent 使用受限 Git 凭据，不能推送主分支/修改仓库设置。
- 开发仅通过 feature 分支与 PR；你人工复核 CI。
- 所有 release 和 token 授权由你的单独凭据完成。

这属于降低风险的操作流程；不能替代 GitHub 平台真正的强制分支规则。
